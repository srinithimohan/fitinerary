# Isolated native Clerk discovery verification

This is a separate authentication-test change. The completed clothing-ownership migration, route validation, ownership tests, target catalog, and original authorization test file are preserved. No production configuration, credentials, policies, or deployment are used.

## Run and isolation

Run `pnpm test:integration` on macOS or Linux with Node 22.12+, the repository's pnpm version, Docker using a local Unix socket, OpenSSL, and tar. Dependency/image downloads require network access. No Clerk account or paid infrastructure is required. Windows named-pipe Docker is explicitly unsupported by this fixture.

For unattended macOS verification, `caffeinate -i pnpm test:integration` holds a temporary idle-sleep assertion for the command's lifetime. It changes no saved power settings and does not resolve host memory pressure.

The runner generates a random project in an unlinked temporary directory. It generates an ES256 project key and an independent RS256 synthetic provider key, matching the algorithm in [Clerk's manual session-verification guide](https://clerk.com/docs/guides/sessions/manual-jwt-verification). The provider private key is never installed as a project signing key. The provider's public JWKS is served by a disposable HTTPS server at `https://clerk.fixture.test`. The server serves only discovery/JWKS documents and records only fixed request paths. It does not proxy or authenticate application traffic.

The exact Linux CLI 3.1.0 binary is downloaded from npm and checked against the SHA-512 integrity in the committed lockfile. Its disposable image uses `node:22.17.0-alpine3.22` and the Docker client from `docker:28.3.3-cli`. The CLI uses Docker DNS and a generated, short-lived fixture certificate trusted only via its process environment. There are no host DNS, hosts-file, global CA, or Docker daemon changes. The fixture has no published ports. Application tests reach only `http://127.0.0.1:55321`; PostgreSQL is published only on `127.0.0.1:55322`.

The HTTPS server runs as the host fixture-file owner, with a read-only root filesystem and no Linux capabilities. Permission to bind its internal port 443 is scoped to that container's network namespace. This avoids assuming that container root can read a host user's 0600 private key on native Linux. The TLS private key is explicitly chmodded to 0600.

Supabase services are pinned to PostgreSQL `17.11.0.018`, Auth `v2.197.0`, PostgREST `v16.5`, and Storage `v1.90.1` using CLI-supported temporary version files. Kong `2.8.1` is supplied by the pinned CLI. The runner checks the actual image version of every service, fails on missing fixture evidence or startup errors, checks both services' configured public JWKS, and checks loopback-only published ports. Image tags are version pins, not immutable digest pins.

The CLI enables `[auth.third_party.clerk]` with the synthetic domain. It must fetch both `/.well-known/openid-configuration` and `/.well-known/jwks.json` after the fixture readiness probe's log has been cleared. Actual PostgREST and Storage receive the public key through the CLI's native discovery machinery. Test JWTs are signed with the independent provider private key, then sent through the ordinary user-scoped Supabase client. No SQL claims injection or shared-secret token is used as native-discovery evidence.

Provider JWTs use RS256 and synthetic session-style `iss`, string `sub`, `sid`, `v`, `nbf`, `iat`, and `exp`, plus the owner-confirmed `role: authenticated` claim. They require no named JWT template or extra `aud` claim. Their ten-minute test lifetime accommodates slow local runs; this is not a claim about production Clerk token lifetime or full session issuance parity.

Cleanup removes only this randomly labeled project's containers, volumes, network, runner image, and temporary files. `node scripts/test-integration.mjs --cleanup` recovers an interrupted run using the ignored local marker. It does not require issuer access, an image rebuild, or global pruning. Cleanup is also attempted automatically on failure/signals. Unrelated Docker resources and the production audit CSV remain untouched.

## Bootstrap correction

The first containerized attempts used unsupported `hostname` and per-service `image` TOML keys. CLI 3.1.0 warned that these were ignored. PostgreSQL could become healthy while the CLI's connection probe still targeted its own container's loopback address. This was an environment configuration error; the canceled `docker stats` request and agent/tool hook timeout did not diagnose a Supabase failure. Exit code 137 alone did not prove an OOM kill; inspected task containers had `OOMKilled=false` and modest memory use.

The runner now uses the supported `SUPABASE_SERVICES_HOSTNAME` for the PostgreSQL Docker DNS name and port 5432, with `api.external_url` pointing separately to Kong's internal DNS name and port 8000. The existing Docker invocation wrapper binds those services to the fixed loopback host ports. Supported version files replace ignored image keys. These changes affect transport/bootstrap only and add no issuer enforcement.

## Assertions and evidence boundaries

The native suite covers valid distinct Clerk-style string subjects, persisted ownership and cross-user isolation, independent untrusted signing keys/issuers, untrusted keys colliding with provider/project key IDs, signature and payload tampering, expiration, an unknown key ID with a trusted signature, and anonymous reads/mutations. Denied inserts/uploads are checked independently for absent persisted rows/objects.

The original same-project-key/wrong-issuer rejection test remains byte-for-byte unchanged. An additional strict rejection assertion uses the **discovered provider key** with a wrong issuer, so the limitation is directly tested through the native path as well. Neither is skipped, inverted into an expected pass, or softened.

The pinned CLI flattens provider and project public keys into a trusted JWKS. PostgREST and Storage do not independently bind those keys to an allowed issuer claim. Discovery authenticates the source of trusted keys; it does not add the missing claim constraint. This local behavior does not establish how Supabase's managed production gateway behaves, and it does not demonstrate that an attacker with an independent private key can forge a valid provider signature. Real Clerk session issuance/login, managed gateway parity, live key rotation, and any production hook configured outside the audited role settings remain unverified.

Primary implementation references: [CLI discovery](https://github.com/supabase/cli/blob/v3.1.0/apps/cli/src/shared/auth/jwks.ts), [CLI JWKS assembly](https://github.com/supabase/cli/blob/v3.1.0/apps/cli/src/command-internal/local-config-values.ts), [supported service hostname](https://github.com/supabase/cli/blob/v3.1.0/apps/cli/src/command-internal/hostname.ts), [PostgREST claim validation](https://github.com/PostgREST/postgrest/blob/v16.5/src/library/PostgREST/Auth/Jwt.hs), and [Storage verification](https://github.com/supabase/storage/blob/v1.90.1/src/internal/auth/jwt.ts).

## Approved CI organization

The verification records above describe the earlier combined command. The owner subsequently approved separating supported guarantees from issuer conformance. `pnpm test:integration` now runs the explicit required file partition; `pnpm test:integration:diagnostic` runs the full superset, including both original issuer callbacks copied verbatim into `issuer-conformance.test.mjs`. `pnpm test:integration:profiles` checks the two original assertion fingerprints. No skip/name filters, expected-failure conversion, exit-status rewriting, or `continue-on-error` is used.

The existing build workflow runs all supported security checks as `Security authorization and authentication`. A separate non-required workflow runs the full issuer diagnostic and fails normally on the unsupported assertions. Both upload only the corresponding sanitized log. Upstream enforcement is tracked in [issue #18](https://github.com/srinithimohan/fitinerary/issues/18).

The current required partition contains 40 assertions; the full diagnostic contains 42 after adding three read-only legacy-reference inventory checks. The issuer limitation remains unsatisfied even when all required checks pass. This fixture cannot prove hosted enforcement or replace a supported issuer-aware component. See [security-pr-boundaries.md](security-pr-boundaries.md) for the exact contexts to require, the staged PR dependency order, and the currently unapplied repository protection payload.
